# Security Policy

Security is fundamental to **Canywhere**. Because Canywhere enables remote inspection and approval of terminal commands and file modifications on developer workstations, our architecture incorporates strict defense-in-depth security principles.

---

## Supported Versions

We provide security updates for the following versions:

| Version | Supported          |
| :------ | :----------------- |
| `0.1.x` | :white_check_mark: |
| `< 0.1` | :x:                |

---

## Reporting a Vulnerability

If you discover a security vulnerability in Canywhere, **please do not open a public GitHub issue or discussion**.

Instead, please report vulnerabilities via one of the following channels:

* **GitHub Security Advisory**: Open a private advisory on GitHub via the [Security Advisories](https://github.com/canywhere/canywhere/security/advisories) tab.
* **Email**: Send an encrypted or confidential email to `security@canywhere.dev`.

### What to Include in Your Report:
* Description of the vulnerability and its potential impact.
* Step-by-step instructions or Proof of Concept (PoC) script to reproduce the issue.
* Affected components (`canywhere-server`, `canywhere-protocol`, `desktop-ui`, `desktop-app`, `mobile/ios`).
* Any proposed mitigations or patches, if available.

### Response Timelines:
* **Initial Acknowledgement**: Within 48 hours of receipt.
* **Assessment & Confirmation**: Within 5 business days.
* **Patch Release & Advisory Publication**: Coordinated with the reporter, typically within 14–30 days depending on severity.

## Security Architecture & Threat Model

Canywhere is designed under a **Zero-Trust Remote Control** model:

### 1. Cryptographic Device Pairing (Ed25519)
* **Single-Use Ephemeral Tokens**: Pairing tokens generated by the Host expire after **5 minutes** and are strictly invalidated upon first use.
* **Asymmetric Key Exchange**: During pairing, clients generate an Ed25519 keypair inside secure hardware (e.g. Apple Secure Enclave / iOS Keychain) and register their public key with the Host.
* **Signed Authentication**: All WebSocket sessions must authenticate using signatures derived from paired keys.

### 2. Execution Guardrails & Remote Approvals
* **Verbatim Command Display**: Remote clients always display the full unescaped shell command string and resolved target directory.
* **Automated Risk Highlighting**: High-risk patterns (e.g. `rm -rf`, `sudo`, destructive git resets, piping into shell) trigger highlighted visual warnings.
* **Diff Verification**: Automated file modification requests require interactive unified diff inspection before permissions are granted.

### 3. Immediate Device Revocation
* Workstation hosts maintain an instant revocation registry in SQLite.
* Revoking a device instantly severs active WebSocket connections and blacklists the client's public key.

### 4. Zero-Persistence Mobile Surface
* Mobile clients maintain no local database of conversation transcripts or execution logs.
* If a mobile device is lost or compromised while disconnected, no local thread or project repository artifacts are stored on the device.
